# 能力知识

## 实体

**能力集合**描述一个函数允许表现出的运行时性质。

**能力知识**描述系统为什么相信某个函数拥有这个能力集合。能力集合参与调用约束；能力知识用于判断结论是否完整、解释结论来源，以及决定哪些反馈对修改者有意义。

**能力来源**是产生能力知识的证据类别：

- 显式声明：由维护者确认的能力边界
- 直接推断：由函数自身可观察的性质得到
- 调用推断：由函数依赖的其他函数得到
- Trait 投票：由同一 trait 方法的多个实现聚合得到
- Port：由架构约定得到的固定端口能力

**分发种子**是 Rivus 维护者确认的底层能力边界。能力推断只依赖“取得一份经过解析的分发种子”这一事实，不依赖种子的运输方式。当前版本把种子编译进 `cargo-rivus`，以后可以在不改变推断和覆盖语义的前提下，改为按 Rust 工具链和目标平台独立更新。

种子承担两类条目。一类是维护者审计过的底层边界（libc syscall、specialization helper 等），它们是能力知识在函数图之下停止解释的基线。另一类是 erased-callback 补丁：当库代码把平台操作作为 `&dyn Fn` 回调传给调度器（如 std 的 `run_path_with_cstr`）时，HIR 函数图无法恢复回调目标，推断会把调度器及其上层入口降为 pure。对这类调度器，种子提供函数级下界：只覆盖路径调度器本身（保守 BI），并对确实执行外部副作用的 wrapper（如文件删除）单独写 BIS；不能给被 env 与网络代码共用的字节串调度器写统一边界，否则会给环境变量访问注入虚假 I。`std::fs` 删除 wrapper、env 读写链的显式 seed 条目即属此类。这类条目是函数图 callback 能力表示缺失时的下界补丁，不是回调能力建模的解决方案；std 在调度器上新增回调类别时必须重新审计。

项目可以提供本地 `seed` 作为显式覆盖，但项目副本不是分发种子的权威来源，也不应成为正常安装的前置条件。`suppress` 和 `ext` 继续表达项目维护者确认的修正。

**完整度**描述能力知识是否覆盖了当前结论所依赖的全部已知路径：

- 完整：所有参与结论的依赖均有能力知识
- 不完整：存在能力未知的依赖，当前集合只能表示已知部分
- 未知：记录保留了能力集合，但原始证据不足以判断完整度

能力来源和完整度是不同维度。显式边界可以是完整的。

## 覆盖

能力记录按有序层级合并。有效顺序是项目 `std`、项目 `deps`、分发种子、项目 `seed`、项目 `suppress`、项目 `ext`，之后才是其他项目层。后出现的同名记录覆盖先出现的记录，但覆盖不得抹去最终记录来自哪个层级和位置。

自动推断在 active `caps/` 目录中只能发布规范生成层：标准库推断写入 `std`，依赖推断写入 `deps`。自定义输出必须位于该目录之外，不能让自动生成内容借助自定义层的更高优先级覆盖人工 `ext` 修正。同一项目的 `infer-std` 和 `infer-capsmap` 通过项目根目录下持久存在的 `.rivus-caps.lock` 串行化；进程内 registry 排斥同进程线程，POSIX record lock 排斥其他进程且不会被 fork 后尚未 exec 的子进程继承。

覆盖改变最终采用的能力知识，不改变被覆盖记录曾经存在的事实。解释工具至少需要指出最终记录的来源；是否保留完整覆盖历史属于诊断细节，不属于能力集合语义。

多个 specialized identity 归一化到同一个可读路径时，能力集合取并集，完整度取其中最弱者；归一化不能把任一不完整 specialization 提升为完整。标准库 trait alias 既参与能力传播也参与完整度传播，alias 记录必须携带投票完整度，并与 caller 推断迭代到固定点后才能发布。

自动推断命令必须发布已经得到的能力下界及其真实完整度。direct external dependency 的函数体、声明签名或 trait vote 若可解析但被不完整依赖污染，`infer-capsmap` 应写出 `completeness=incomplete`，不能把它降格为完全 unknown 并要求维护者为每个 wrapper 伪造显式边界。同一可解析声明的函数体、签名和投票各自证明的能力取并集；组合结果不能由投票证据单独表达时，记录使用 inferred 来源，不能伪造与能力集合不一致的 trait vote。只有 resolver 没有函数体、声明、trait 实现或现有能力记录可用时，命令才因 opaque unknown 边界停止。

自动生成的 trait alias 是派生知识，不能覆盖人工提供的 `seed` 或 `suppress` 记录。固定点迭代和最终输出都必须保留人工记录的能力集合、来源与完整度；派生 alias 只填补尚无权威记录的路径。

新生成的记录不保证一定完整。若函数体不可见、调用边界 opaque，或 trait vote 包含不完整实现，生成器必须发布已证明的能力下界并保留 `incomplete`，而不是伪造完整知识。重复运行相同生成命令且没有增加证据时，结果可以保持不完整。

incomplete 诊断必须区分来源不明的旧记录和新推断知识。来源不明的记录建议重新生成；新推断知识必须指出它是保守下界，并提供可继续检查的 callee、trait 实现或 opaque 边界，不能谎称重新生成必然消除警告。`<inference>` 是检查时计算结果，不是可刷新的 caps layer。

incomplete 知识按知识根因（root）分组发射：一条 caps record 是一个根（精确键与 readable 回退键解析到同一 record 的多个 specialization 合并为一个根），一条 inference root（ghost、bodyless、artifact、不稳定 vote）也是一个根。每个被本地直接调用的根因产生一条 warning，数量等于根因数，不随调用点或受影响 caller 数量增长；每条 warning 携带 root 的具体成因（root kind）与针对该成因的修复指引。record root 的诊断以 `file:line` 定位其 caps record——同一 readable path 下多个 exact record 也保持可区分。诊断锚定该根因的第一个精确调用点，且诊断中命名的 identity 与锚点来自同一 usage；没有调用点时退回第一个 caller 的函数锚点。直接 caller 保留在诊断 details（前 5 个加溢出计数；传递性受影响函数不逐个列出）中，但绝不作为独立 warning 锚点发射。同一根因的多个 crate 身份（同 def_path 不同 crate_id）合并为一条。ghost callee 的知识 basis 是 `none`（它不存在于任何知识层），其修复指引与 unknown-callee 诊断一致：先刷新生成层，剩余路径进项目修正层。重跑推断后仍 incomplete 的记录走手工标定路径：std 记录写 explicit complete 记录并在记录上方用 `#` 注释写明依据（来源、版本、验证方式），依赖记录在 `caps/ext` 同样手工标定并写注释；分发 seed 的维护者把 std 标定合入仓库 `caps/seed`（惠及所有消费者），普通项目写项目自己的 `caps/seed` 覆盖层。Rivus lint 属性只在 crate root 生效。

推断输入在一次分析中是不可变知识视图：基础 caps 层与目标范围内 Port 方法按优先级查询。准备分析预先建立反向调用依赖和 trait 实现依赖；能力与完整度在同一快照上分别运行一次工作队列传播，生成的 trait alias 在固定点之后物化，不能通过复制 capsmap 并重新扫描整图来反复注入。分析也不能为了增加临时知识而复制整张调用图。

## Trait 投票

trait 方法可能有多个行为不同的实现。系统只对 `B/I/P/S/T` 五个可传播能力逐项计票，达到既定阈值的能力进入该 trait 方法的典型完整能力；`A/C/U` 是方法自身的签名或安全能力，不参加投票，也不进入后缀。`M` 同样由签名测量，但它与 B/I/P/S/T 一样是合法的后缀字母。

投票结果表达典型行为，不表达所有实现的最坏情况，也不证明每个实现都符合结果。

一份完整投票知识包含：

- 参与投票的实现数量
- 每个可传播能力的得票数
- 选中能力所使用的阈值
- 最终选中的能力集合

World Port 不参与 `B/I/S/T` 投票——其公开契约固定为 `P`，序列化知识是 `basis=port, caps=P, complete`；实现效果是审计信息，通过 report 和 why 查看。向调用方传播时，任何包含 P 的契约都投影为仅 P，因此实现效果不会穿过端口边界。Port 实现不产生普通 trait 的非典型实现 warning。

## 非典型实现

如果一个完整、可修改的普通 trait 实现拥有投票结果未选中的可传播能力，该实现是一个**非典型实现**。

非典型实现不改变投票结果，也不自动使 trait 进入严格契约模式。它产生设计反馈，提醒修改者检查该实现是否把隐藏环境、I/O、阻塞或其他副作用放进了一个通常不具备这些行为的抽象。

以下情况不产生非典型实现反馈：

- 实现或投票知识不完整
- 实现不是当前工作范围内可修改的源码
- trait 是 Port
- 差异只包含不传播的签名/函数体能力（A/C/U 从签名或函数体事实测量，名字后缀只携带 B/I/M/P/S/T）
- 实现缺少某个已被多数实现选中的能力

最后一种情况不是异常：一个能力更少的实现可以满足一个允许更多行为的典型接口。

## 使用规则

调用检查只消费能力集合。解释、报告和设计反馈同时消费能力知识。

未知能力知识不能被当作纯函数。不完整的空能力下界表示"尚无已知能力"，不能显示为"纯函数"。解释输出必须保留"不完整"和"完整度未知"的区别。推断不完整时，解释工具不得声称声明中存在多余能力。

fresh 生成的 `caps/std` 与分发 seed 合并后的有效能力可以比生成层自身的记录更强：公共 wrapper 的推断记录可能缺少被 seed 边界固定住的 callee 能力。判断最终契约时必须查询 effective caps（如 `cargo rivus why`），不能只读生成层。

解释工具只能从当前已加载的实现图列出导致 trait 投票不完整的具体实现。持久化投票只保存实现数量、阈值和票数；没有实现图时，不能从聚合记录伪造实现路径。

Trait 投票详情不会改变 pure、good 和 ok 的定义。非典型实现反馈也不改变能力统计；它用于指出可能改善统计结果的重构位置。
