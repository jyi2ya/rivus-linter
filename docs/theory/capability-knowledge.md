# 能力知识

## 实体

**能力集合**描述一个函数允许表现出的运行时性质。

**能力知识**描述系统为什么相信某个函数拥有这个能力集合。能力集合参与调用约束；能力知识用于判断结论是否完整、解释结论来源，以及决定哪些反馈对修改者有意义。

**能力来源**是产生能力知识的证据类别：

- 显式声明：由维护者确认的能力边界
- 直接推断：由函数自身可观察的性质得到
- 调用推断：由函数依赖的其他函数得到
- Trait 投票：由同一 trait 方法的多个实现聚合得到
- Port：由架构约定得到的固定端口能力
- 迁移记录：从不携带来源信息的旧能力记录转换得到

**完整度**描述能力知识是否覆盖了当前结论所依赖的全部已知路径：

- 完整：所有参与结论的依赖均有能力知识
- 不完整：存在能力未知的依赖，当前集合只能表示已知部分
- 未知：记录保留了能力集合，但原始证据不足以判断完整度

能力来源和完整度是不同维度。显式边界可以是完整的；迁移记录可以继续提供能力集合，但其历史推断证据已经不可恢复。

## 覆盖

能力记录按有序层级合并。后出现的同名记录覆盖先出现的记录，但覆盖不得抹去最终记录来自哪个层级和位置。

覆盖改变最终采用的能力知识，不改变被覆盖记录曾经存在的事实。解释工具至少需要指出最终记录的来源；是否保留完整覆盖历史属于诊断细节，不属于能力集合语义。

自动推断命令必须发布已经得到的能力下界及其真实完整度。direct external dependency 的函数体、声明签名或 trait vote 若可解析但被不完整依赖污染，`infer-capsmap` 应写出 `completeness=incomplete`，不能把它降格为完全 unknown 并要求维护者为每个 wrapper 伪造显式边界。同一可解析声明的函数体、签名和投票各自证明的能力取并集；组合结果不能由投票证据单独表达时，记录使用 inferred 来源，不能伪造与能力集合不一致的 trait vote。只有 resolver 没有函数体、声明、trait 实现或现有能力记录可用时，命令才因 opaque unknown 边界停止。

多个 specialized identity 归一化到同一个可读路径时，能力集合取并集，完整度取其中最弱者；归一化不能把任一不完整 specialization 提升为完整。标准库 trait alias 既参与能力传播也参与完整度传播，alias 记录必须携带投票完整度，并与 caller 推断迭代到固定点后才能发布。

自动生成的 trait alias 是派生知识，不能覆盖人工提供的 `seed` 或 `suppress` 记录。固定点迭代和最终输出都必须保留人工记录的能力集合、来源与完整度；派生 alias 只填补尚无权威记录的路径。

## Trait 投票

普通非 Port trait 方法可能有多个行为不同的实现。系统对每个可传播能力独立计票，达到既定阈值的能力进入该 trait 方法的典型公开能力。

投票结果表达典型行为，不表达所有实现的最坏情况，也不证明每个实现都符合结果。

一份完整投票知识包含：

- 参与投票的实现数量
- 每个可传播能力的得票数
- 选中能力所使用的阈值
- 最终选中的能力集合

Port 方法不参与投票，其公开能力固定为 Port。

## 非典型实现

如果一个完整、可修改的普通 trait 实现拥有投票结果未选中的可传播能力，该实现是一个**非典型实现**。

非典型实现不改变投票结果，也不自动使 trait 进入严格契约模式。它产生设计反馈，提醒修改者检查该实现是否把隐藏环境、I/O、阻塞或其他副作用放进了一个通常不具备这些行为的抽象。

以下情况不产生非典型实现反馈：

- 实现或投票知识不完整
- 实现不是当前工作范围内可修改的源码
- trait 是 Port
- 差异只包含不传播的签名能力
- 实现缺少某个已被多数实现选中的能力

最后一种情况不是异常：一个能力更少的实现可以满足一个允许更多行为的典型接口。

## 使用规则

调用检查只消费能力集合。解释、报告和设计反馈同时消费能力知识。

未知能力知识不能被当作纯函数。不完整的空能力下界表示“尚无已知能力”，不能显示为“纯函数”。解释输出必须保留“不完整”和“完整度未知”的区别，不能把迁移记录的未知完整度改写成推断不完整。推断不完整时，解释工具不得声称声明中存在多余能力。

解释工具只能从当前已加载的实现图列出导致 trait 投票不完整的具体实现。持久化投票只保存实现数量、阈值和票数；没有实现图时，不能从聚合记录伪造实现路径。

Trait 投票详情不会改变 pure、good 和 ok 的定义。非典型实现反馈也不改变能力统计；它用于指出可能改善统计结果的重构位置。

## 迁移

旧能力记录只保存路径和能力集合。迁移必须保证：

- 每个路径的能力集合保持不变
- 每个层级中的记录保持在原层级
- 层级覆盖后的最终能力集合保持不变
- 迁移失败时原记录整体保持可用

旧记录无法恢复的投票票数、推断路径和完整度不得伪造。已知人工维护的 `seed`、`suppress` 和 `ext` 层迁移为显式来源；`std`、`deps` 和来源不明的自定义层迁移为旧记录来源，其完整度为未知。后续重新推断可以用新的完整证据替换迁移记录。

目录发布分为原子交换和 no-replace 备份发布。备份发布失败时必须尝试交换回原目录；如果回滚交换本身失败，系统必须保留装有原 v1 数据的 staging 目录并在错误中报告其位置，不能声称原路径已恢复。

同一项目的迁移和自动推断写入必须使用同一个项目锁串行化，不能让 staging、推断输出和目录交换交叉发生。锁由项目根目录下持久存在的 `.rivus-caps.lock` regular file 承载：进程内 registry 排斥同进程线程，POSIX record lock 排斥其他进程且不会被 fork 后尚未 exec 的子进程继承。迁移在交换前重新验证 v1 source，但不遵守锁的外部编辑器无法被强制互斥，因此迁移期间不得手工修改 `caps/`。迁移后的 v2 目录和每个同名 layer 必须继承原 v1 对象的权限；权限读取和应用都不能跟随符号链接。交换出的 v1 树在发布 backup 或完成中断恢复前必须同步每个 layer 和目录本身，不能只同步新的 active v2。进程若在交换后中断，active v2 目录中的 transaction marker 必须精确指出原 v1 staging；后续迁移只有在该 staging 或已经发布的 backup 与当前 v2 的逐层语义一致且完成持久化时才能完成恢复。staging 与 backup 同时存在、同时缺失或内容不匹配时必须停止并交由维护者判断。

迁移输入目录中的 layer 必须是 regular file。对 symlink 或子目录进行隐式跟随或忽略会让原目录与新目录的内容集合不一致，因此迁移必须显式拒绝。
